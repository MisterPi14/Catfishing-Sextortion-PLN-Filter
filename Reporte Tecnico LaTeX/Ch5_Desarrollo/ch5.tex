En adición a la parte técnica, el proyecto contempló bajo una metodología, la obtención de datos reales sobre estafa, puntualmente ejemplos de mensajería fraudulenta que busca explotar a la víctima mediante métodos afines al catfishing y la sextorsión.

Se llevo a cabo una investigación en foros de Internet como reddit \cite{RedditFlirtu2025} con el objetivo de encontrar una aplicación de mensajería con reportes frecuentes de estafas.

Los resultados de esta primera fase arrojaron una aplicación candidata por las características difundidas por sus usuarios en el uso de esta plataforma. Se trata de un chat de citas llamado Flirt U, en sentido estricto, un bot de telegram el cual se utiliza dentro de dicha plataforma.

\subsection{Metodología: Perfil señuelo}

Esta tarea involucró al realizar una cuenta señuelo para poder identificar y contactar con posibles estafadores dentro de la aplicación de citas.

El objetivo de esta etapa fue puntualmente, determinar cuáles eran los patrones clave de cada tipo de estafa: cafishing y la sextorsión así como el estilo del lenguaje y la forma de la comunicación que se suele llevar a cabo por parte de los estafadores por un lado para la generación sintética de los datos y para la obtención principalmente de datos reales.

La recolección de datos se remitió exclusivamente a medios de texto, no se contempló imagen.

\subsection{Hallazgoz clave de la investigacion controlada en flirtu}

De los atacantes
* Se encontro que los estafadores de manera contraintuitiva con parte de los datos sinteticos, suelen pedir con frecuencia realizar videollamadas y efectivamente se registraron casos en los cuales del lado del atacante se visualizaban videos "posiblemente falsos con el fin de otorgar confianza en los estafadores"

\subsubsection{Características sobre el catfishing}

\begin{itemize}
    \item Crear historias difíciles para generar empatía en la víctima
    \item Establecer una comunicación que parezca genuina con fin de conectar con la víctima y establecer un lazo de confianza que posteriormente puedan explotar para obtener beneficios
    \item Las solicitudes que efectúan a las víctimas pueden tener diferentes técnicas psicológicas
    \item Solicitar tarjetas de pago, dinero o fotos
    \item Algunos perfiles aprovechaban la conexión emocional para reclutar participantes en grupos de inversión en criptomonedas, cuyas motivaciones no son identificadas en la investigación
    \item Constante solicitudes para acordar realizar una videollamada de carater intimo, mayormente con el objetivo de recabar imagenes privadas con fines de sextorsion y para utilizar posteriormente en el ejercicio de catfishing con otras victimas.
    \item Enviar contenido de caracter explicito en ocasiones coherente en algunas ocasiones con la identidad falsa, con el fin de generar credibilidad.
\end{itemize}

\subsubsection{Características de la sextorsión} 
\begin{itemize}
    \item Solicitan perfil de redes sociales personales con propósitos como:
        \begin{itemize}
            \item Conocer detalles personales de la víctima
            \item Potencialmente acceder a la red de contactos de la persona para después chantajear tras recibir material explícito
        \end{itemize}
    \item Solicitar contenido particularmente explicito, fotografias o videos.
    \item Usar contenido privado de las victimas para extorcionar bajo la amenaza de publicarlo o enviarlo a cercanos, jefes, parientes con motivaciones variadas, siendo las principales dinero o más material explicito.
\end{itemize}

    def evaluate_model(model_name, dataset_to_use, additional_examples_text="", dictionary_text=""):
    """Ejecuta todas las predicciones y calcula metricas para un modelo especifico."""
    y_true, y_pred_raw, y_pred_leaked = [], [], []
    prediction_times = []
    
    total_start_time = time.time()
    print(f"Evaluando {len(dataset_to_use)} muestras con el modelo {model_name}...")

    print("Progreso: 0%", end="")

    for i, sample in enumerate(dataset_to_use, 1):        
        individual_pred_start_time = time.time()
        rawPrediction, leakedPrediction = get_model_prediction(model_name, sample['text'], additional_examples_text, dictionary_text)
        individual_pred_end_time = time.time()
        
        y_true.append(sample['label'])
        y_pred_raw.append(rawPrediction)
        y_pred_leaked.append(leakedPrediction)
        prediction_times.append(individual_pred_end_time - individual_pred_start_time)

        percentage = (i / len(dataset_to_use)) * 100
        print(f"\rProgreso: {percentage:.1f}% ({i}/{len(dataset_to_use)} muestras)", end="", flush=True)
    
    total_end_time = time.time()
    total_evaluation_time = total_end_time - total_start_time
    
    print(f"\nCompletado: {len(dataset_to_use)} muestras procesadas para {model_name}.")
    
    possible_labels = sorted(list(set(y_true)))#se usa set para que no existan etiquetas repetidos
    report_dict = classification_report(y_true, y_pred_leaked, output_dict=True, zero_division=0, labels=possible_labels)
    report_dict['accuracy'] = accuracy_score(y_true, y_pred_leaked)
    timing_metrics = {
        'total_evaluation_time_seconds': total_evaluation_time,
        'average_time_per_prediction_seconds': statistics.mean(prediction_times) if prediction_times else 0,
        'min_prediction_time_seconds': min(prediction_times) if prediction_times else 0,
        'max_prediction_time_seconds': max(prediction_times) if prediction_times else 0,
        'samples_per_second': len(dataset_to_use) / total_evaluation_time if total_evaluation_time > 0 else 0,
        'total_evaluation_time_minutes': total_evaluation_time / 60
    }
    
    return {
        'labels' : {'etiquetas_reales':y_true, 'llm-output-predictions':y_pred_raw, 'leaked-prediction': y_pred_leaked},
        'classification_report': report_dict,
        'timing_metrics': timing_metrics
    }
\end{lstlisting}

\subsection{Descripción de la arquitectura por servicio de Amazon web services}

La arquitectura propuesta representa una solución híbrida nube-local diseñada para implementar un sistema de mensajería instantánea con capacidades de detección de amenazas por estafa en modalidad de catfishing y/o sextorsión. La arquitectura está construida con el objetivo de operar dentro de la capa gratuita de AWS, es una solucion implementada bajo servicios serverless que eliminan la necesidad de aprovisionamiento en nube. El sistema está diseñado para detectar técnicas de sextorsión y catfishing en conversaciones de chat, alertando a los usuarios de manera preventiva cuando se identifiquen patrones de riesgo, mientras se cuenta con persistencia de datos y se entrega un sistema de mensajería funcional.

\subsubsection{1. AWS AMPLIFY HOSTING (Frontend)}

AWS Amplify es un servicio de aws empleado para alojar y servir el front end de la aplicacion web, el lado del cliente. Este seervicio permite desplegar aplicaciones desde repositorios Git.

Su funcion es servir los archivos estaticos del front end que incluyen html, css y JavaScript, es compatible con el certificado SSL/TLS por lo que sirve conexiones seguras a traves de HTTPS. 

Su uso dentro del presente proyecto radica en simplificar la complejidad del desarrollo en relacion a la configuracion de servidores web y aspectos relacionados a la gestion certificados SSL. De entre las caracteristicas por las que se contempla dentro del proyecto es su generosa capa gratuita que incluye 15GB de almacenamiento en la infraestructura de AWS asi como la compatibilidad con los demas servicios de la capa gratuita de AWS. 

\subsubsection{2. AMAZON COGNITO USER POOL (Autenticación)}

Amazon Cognito User Pool es un servicio de AWS orientado a la autenticación de usuarios, maneja funcionalidades desde el registro hasta la recuperación de credenciales.

Su funcion es servir como un sistema de autenticacion estable, gracias a que esta basado en estandares como OAuth 2.0 y OpenID Connect. mediante la generacion de Json Web Tokens permiten validar las credenciales de usuarios, estos son empleados para autorizar peticiones hacia API Gateway y otros servicios dentro del ecosistema AWS. 

Su uso dentro del presente proyecto es requerido para implementar un sistema de autentificacion seguro, lo cual es un proyecto de amplia madurez y complejidad en si mismo, ademas de ser propenso a vulnerabilidades. Cognito provee de una solucion robusta que brinda hash de contraseñas bcrypt, protección contra ataques de fuerza bruta, verificación de email, y cumplimiento con estándares de seguridad.

\subsubsection{3. API GATEWAY WEBSOCKET API (Comunicación en tiempo síncrono.)}

API Gateway con soporte WebSocket es el servicio dentro de AWS que establece conexiones bidireccionales entre clientes y backend, permitiendo la comunicación en tiempo síncrono.

Su funcion es servir como medio de enlace con cada uno de los clientes que consumen la aplicacion, este asigna un connectionId a cada sesión. Entre otras cosas gestiona el envio de los mensajes dentro de la aplicación, esta es la responsable del enrrutamiento hacia la funcion Lambda dependiento del flujo de datos, ejemplos como "enviar mensaje", "obtener historial", "recibir mensaje". También sera empleado por el requierimiento de envio de mensajes desde el backend hasta los clientes para gestionar el alertamiento oportuno mediante mensajes que lleguen a la inferaz de usuario.

Su uso es requerido dentro del proyecto en alineacion con el objetivo del diseño de un sistema de mnsajeria similar a los medios de redes sociales actuales como WhatsApp o Telegram, en estos casos se emplea una comunicación bidireccional de tiempo sincrono, esto se lograra mediante una API de tipo WebSocket las cuales mantienen una conexion TCP persistente que permite comunicacion bidireccional, el servicio de AWS tiene incorporadas caracteristicas propias de los sistemas de comunicación como lo son el manejo de errores y la reconexión, en adición posee la integración con AWS Lambda. 

\subsubsection{4. AWS LAMBDA - ReceiveMessage (Procesamiento de Mensajes Entrantes)}

Las funciones Lambda de AWS son su alternativa a las denominadas funciones serverless, caracterizadas por no requeriri aprovisionamiento de alli la descripcion serverless equivalente a "sin servidor".

La funcion de este servicio se concentra en el procesamiento de la logica de programacion definida, algunas de sus tareas incluyen: Almacenar los mensajes recibidos en la base de datos de AWS dynamodb, Encolar el mensaje empleando el servicio AWS SQS para su analisis posterior por parte del worker local (el modelo gestionado en maquina local) y Reenviar el mensaje a su destinatario a traves del servicio AWS API Gateway WebSocket.

Su uso en el proyecto es fundamental para la implementacion de la logica del backend, son requeridas de igual manera para la gestion de la logica de desacoplamiento asincrono gracias a la encolacion desde SQS se consigue que el procesamiento de la inferencia del LLM en el worker local sea independiente del flujo de datos principal perteneciente a la funcionalidad del sistema de mensajeria, de esta manera la ejecución del modelo no retraza el envio y recepcion de mensajes, en adicion una de las principales caracteristicas de las funciones lambda es la facturacion la cual puede ser en funcion de las ejecuciones lo cual ahorra costes de aprovisionamiento despediciado y solo se cobra por las ejecuciones realizadas.

\subsubsection{5. AWS LAMBDA - GetMessages (Recuperación de Historial)}

Esta función Lambda maneja las solicitudes de los usuarios para recuperar el historial de conversaciones anteriores.

Funcionalidad: Cuando un usuario abre una conversación o solicita mensajes antiguos, esta función consulta DynamoDB usando el conversationId como clave de partición y recupera todos los mensajes ordenados por timestamp. Formatea los resultados incluyendo el contenido del mensaje, información del remitente, estado de análisis, y cualquier alerta de riesgo detectada.

Por qué es necesario: Separar la lógica de recuperación de historial en una función dedicada sigue el principio de responsabilidad única y permite optimizar las consultas a DynamoDB de forma independiente. Esta función puede implementar paginación para conversaciones largas, filtrado por fecha, y caché de resultados frecuentes sin afectar el rendimiento del envío de mensajes. La separación también facilita agregar funcionalidades futuras como búsqueda de mensajes o exportación de conversaciones.

\subsubsection{6. AWS LAMBDA - NotifyUser (Sistema de Alertas)}

Esta función Lambda se encarga de enviar notificaciones a los usuarios cuando el sistema de análisis detecta contenido de riesgo en los mensajes.

Funcionalidad: El Worker local invoca esta función cuando el LLM identifica patrones de catfishing o sextorsión. La función consulta DynamoDB para obtener el connectionId del usuario que debe ser alertado, construye un mensaje de alerta con detalles del riesgo detectado (tipo de amenaza), y lo envía a través de API Gateway WebSocket directamente al cliente conectado.

Por qué es necesario: Las alertas de seguridad deben entregarse de forma inmediata y confiable. Esta función centraliza la lógica de notificaciones, permitiendo implementar canales de alerta (WebSocket) desde un único punto. Al ser invocada por el Worker local, mantiene el desacoplamiento entre el sistema de análisis y la infraestructura de AWS. También permite implementar lógica de negocio como evitar alertas duplicadas, escalar alertas según severidad, o registrar todas las notificaciones para auditoría.

\subsubsection{7. AMAZON DYNAMODB (Persistencia de Datos)}

DynamoDB es la base de datos NoSQL completamente administrada que almacena todos los datos del sistema: mensajes, metadatos de conversaciones, y estados de conexión.

Funcionalidad: La tabla ChatMessages utiliza un modelo de datos optimizado con conversationId como clave de partición (PK) y timestamp como clave de ordenamiento (SK). Esto permite consultas eficientes de todos los mensajes de una conversación ordenados cronológicamente. Cada registro almacena: messageId, senderId, receiverId, content (contenido del mensaje), status (pendiente/analizado), analysisResult (resultado del LLM), connectionId (para enrutamiento WebSocket), y metadatos adicionales.

Por qué es necesario: DynamoDB ofrece latencia de milisegundos de un solo dígito, escalamiento automático, y alta disponibilidad sin gestión de servidores. Para un MVP de chat, estas características son críticas: las consultas de historial deben ser rápidas, el sistema debe manejar picos de escritura cuando múltiples mensajes llegan simultáneamente, y los datos deben estar siempre disponibles. Su modelo de precios bajo demanda significa que solo se paga por las operaciones realmente ejecutadas. La capa gratuita incluye 25GB de almacenamiento y 25 unidades de capacidad de lectura/escritura, suficiente para miles de mensajes. El diseño de clave compuesta (PK + SK) permite consultas eficientes sin índices secundarios costosos.

\subsubsection{8. AMAZON SQS - MessageAnalysisQueue (Cola de Análisis)}

Amazon SQS (Simple Queue Service) es el servicio de cola de mensajes que actúa como buffer entre el sistema de chat en AWS y el Worker local que ejecuta el LLM.

Funcionalidad: Cada mensaje de chat se encola en SQS inmediatamente después de ser almacenado en DynamoDB. La cola está configurada con long-polling (WaitTimeSeconds: 20s) para reducir solicitudes vacías y costos. El Worker local consulta continuamente esta cola, procesa los mensajes con el LLM, y los elimina de la cola solo después de actualizar exitosamente DynamoDB. Si un mensaje falla 3 veces (por ejemplo, por errores del LLM), se mueve automáticamente a la Dead Letter Queue (DLQ).

Por qué es necesario: SQS es fundamental para la tolerancia a fallos del sistema. Si la computadora local con Ollama está apagada o sin conexión, los mensajes permanecen en la cola hasta por 14 días, garantizando que ningún mensaje quede sin analizar. El VisibilityTimeout de 300 segundos asegura que si el Worker falla durante el procesamiento, el mensaje vuelve a estar disponible automáticamente. La DLQ captura mensajes problemáticos para investigación manual sin bloquear el procesamiento de mensajes válidos. SQS también desacopla completamente el ritmo de envío de mensajes del ritmo de análisis del LLM, permitiendo que el chat funcione con baja latencia incluso si el análisis toma varios segundos. La capa gratuita incluye 1 millón de solicitudes mensuales.

\subsubsection{9. AMAZON SQS - Dead Letter Queue (Gestión de Fallos)}

La DLQ es una cola secundaria que recibe mensajes que no pudieron ser procesados exitosamente después de múltiples intentos.

Funcionalidad: Cuando un mensaje en MessageAnalysisQueue falla 3 veces consecutivas (configurado en maxReceiveCount), SQS lo mueve automáticamente a la DLQ. Estos mensajes quedan disponibles para inspección manual, reprocesamiento con parámetros ajustados, o análisis de patrones de fallo.

Por qué es necesario: Sin una DLQ, los mensajes problemáticos podrían bloquear la cola principal en un ciclo infinito de reintentos, consumiendo recursos y retrasando el procesamiento de mensajes válidos. La DLQ permite identificar problemas sistemáticos (por ejemplo, un tipo de contenido que causa errores en el LLM) sin perder datos ni afectar la operación normal. También proporciona visibilidad sobre la tasa de fallos del sistema, un indicador clave de salud para el MVP.

\subsubsection{10. WORKER LOCAL + OLLAMA LLM (Análisis de Contenido)}

El Worker es una aplicación Python que se ejecuta en una computadora local y actúa como puente entre AWS y el modelo de lenguaje Ollama.

Funcionalidad: El Worker ejecuta un bucle continuo que: (1) Consulta SQS con long-polling para obtener mensajes pendientes, (2) Extrae el contenido del mensaje y lo envía a la API de Ollama (localhost:11434) con un prompt especializado para detectar catfishing y sextorsión, (3) Recibe la respuesta del LLM con clasificación de riesgo, etiquetas de amenaza, y nivel de confianza, (4) Actualiza el registro en DynamoDB cambiando el status a "analizado" y guardando el resultado, (5) Si se detecta riesgo alto, invoca la función Lambda NotifyUser para alertar al usuario, y (6) Elimina el mensaje de SQS solo después de confirmar todas las operaciones.

Por qué es necesario: Ejecutar el LLM localmente es un requisito del proyecto que reduce costos significativamente (evita pagar por inferencia en AWS SageMaker o Bedrock) y permite usar una variedad de modelos largos de lenguaje para la detección de catfishing/sextorsión. El Worker requiere permisos IAM para: sqs:ReceiveMessage, sqs:DeleteMessage (interactuar con la cola), dynamodb:UpdateItem (actualizar resultados), y lambda:InvokeFunction (enviar alertas). 

Para estos efectos se consideran modelos con escalas de entre 0.5 billones de parametros hasta 8 billones de parametros. Se contempla aprovisionamiento local en una instancia de computo on-premise para la ejecución de la inferencia de los distintos modelos con las siguientes caracteristicas de hardware: (CPU Intel(R) Core(TM) i7-4770 4ª generación  basada en la arquitectura Haswell Frecuencia base de 3.40GHz, GPU Nvidia GeForce GTX 1060 6GB Vram, 16GB Ram del sistema con frecuencia de 1600 MHz, Almacenamiento persistente ADATA HD720 SCSI 1.8 terabytes). Este diseño permite actualizar el modelo o ajustar prompts sin modificar la infraestructura de AWS.

\subsubsection{Conclusión sobre la arquitectura}

Esta arquitectura representa una solución pragmática y económica para el MVP, aprovechando servicios serverless de AWS que operan completamente dentro de la capa gratuita para volúmenes de prueba. El diseño prioriza la simplicidad operacional (sin servidores que gestionar), la tolerancia a fallos (SQS + DynamoDB garantizan que ningún mensaje se pierda), y la flexibilidad (el Worker local puede actualizarse independientemente). La separación de responsabilidades entre componentes facilita el desarrollo iterativo y el debugging, mientras que el uso de servicios administrados reduce el tiempo de implementación y los riesgos de seguridad. El sistema está preparado para escalar agregando más Workers locales si el volumen de mensajes aumenta, o migrando el LLM a AWS cuando el presupuesto lo permita.
